# Passession + OMP + Kiro HTTP 0.6.1

## 작업 중 SSO 인증 갱신 연결이 막힐 수 있는 프록시 결함 수정

0.6.0의 네이티브 프록시는 HTTPS/웹소켓 연결이 유지되는 동안 신규 연결 처리 스레드를 계속 점유했습니다. 8개가 점유되면 뒤늦게 필요한 SSO 토큰 갱신 등 새 연결이 대기할 수 있었습니다. 0.6.1에서는 유지 연결을 별도 I/O 루프에서 처리하여 신규 연결 처리를 막지 않도록 수정했습니다.

- 기존 연결을 강제로 종료하지 않고 새로운 인증·모델 연결을 처리합니다.
- 유지 터널은 최대 128개입니다. 한도 초과는 새 연결에 502를 반환하며, 연결이 종료되면 재시작 없이 자리를 재사용합니다.
- 양방향 데이터·TCP 반닫힘·로컬 프록시 인증·Windows Negotiate/NTLM·TLS 검증을 유지합니다.
- 토큰 재발급 요청의 재시도 정책과 사용자 인증 DB 형식은 변경하지 않습니다.
- Passession 0.13.15, OMP 18.20.0, omp-kiro 0.4.8 및 동봉 유틸리티 버전은 0.6.0과 동일합니다.

## 업데이트

1. 기존 설치 폴더에서 `stop.cmd`를 실행하고 Passession 앱도 종료합니다.
2. 새 ZIP 전체를 **새 폴더**에 풉니다. 기존 폴더에 덮어쓰지 마세요.
3. 새 폴더에서 `setup.cmd`를 수행하고 `start.cmd`로 실행합니다.
4. 동일한 사용자와 데이터 경로를 사용하면 기존 인증·설정·대화 기록을 유지합니다. 별도 `--data-dir`를 사용했다면 같은 경로를 지정하세요. 인증 DB 삭제나 토큰 복사는 필요하지 않습니다.

앱 시작 시 기존 Paseo의 Windows 알림 등록에 영향을 줄 수 있는 upstream 동작은 그대로입니다. 이를 허용하지 않는 환경에서는 `start.cmd --no-app`과 CLI를 사용하세요.

## 검증 범위와 한계

Windows의 실제 네이티브 프록시와 제어된 TLS 서버로 다음을 확인했습니다.

- 16개 연결을 유지한 상태에서 서울 리전 Identity Center `/token` 경로로 동일 프로세스의 토큰 갱신을 두 번 수행하고, 회전된 refresh token 저장·재사용과 기존 연결의 실제 데이터 보존을 확인했습니다.
- 128개 터널의 상한 거부, 연결 종료 후 재사용, 기존 연결 데이터 보존을 확인했습니다.
- 반닫힘 후 응답 전달과 Windows `AcceptSecurityContext`를 이용한 실제 Negotiate HTTP/CONNECT 인증을 확인했습니다.

합성 테스트용 계정만 사용했으며 기존 로컬 회사 계정은 변경하지 않았습니다. 이 결과는 실제 AWS SSO·회사 프록시 정책·사용자에게 발생한 오류의 최종 원인 확정 또는 현장 해결 확인을 뜻하지 않습니다. GUI 실행과 Windows Server 2019는 미검증입니다.

`Cannot reach AWS SSO OIDC`가 계속되면 회사망에서 `https://oidc.<실제 SSO 리전>.amazonaws.com/token` 접근이 허용되는지 확인하세요. 인증서 검증을 끄거나 승인 없이 DIRECT로 우회하지 마세요. 배포 ZIP의 최종 CI 실행·소스 SHA·해시는 아래 배포 무결성 항목을 기준으로 확인하세요.
